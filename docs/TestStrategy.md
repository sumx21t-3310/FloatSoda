# テスト戦略

このドキュメントは、FloatSoda のテストを「範囲 × 目的 × オラクル」の3軸で整理し、現在の配置と既知の穴をまとめたものです。テストの命名と「何を検証するか」の観点は [CONTRIBUTING.md](../CONTRIBUTING.md) が正典であり、本ページはそれに代わるものではありません。本ページは、テストの配置を決めるための地図として使います。

## 1. 3つの軸

テストの種類は1本の軸では整理できません。次の3軸に分けて考えます。

| 軸 | 値 | 意味 |
|---|---|---|
| 範囲 | 単体 / 結合 / 描画 / 実機 | どこまで結合して動かすか |
| 目的 | 機能 / 回帰 / 非機能 / 受け入れ | 何を確かめるか |
| オラクル | 例示 / 不変条件 / ゴールデン / 差分 | 期待値をどう定義するか |

範囲の4値は FloatSoda の構造に対応します。

| 範囲 | 対象 | 実行手段 |
|---|---|---|
| 単体 | ジオメトリ型、RenderObject 1個、Widget 1個 | `dotnet test` |
| 結合 | `WidgetBinding` から `RenderPipeline` までを通した経路。差分更新、入力の配送 | `dotnet test` |
| 描画 | `FloatSoda.Testing` のビットマップ描画による画素 | `dotnet test` |
| 実機 | SteamVR が動いている状態でしか観測できないもの。オーバーレイハンドル、コントローラーの座標、レンダースレッドの GL コンテキスト | HMD を着けて手動で操作する(`.agents/skills/floatsoda-device-test`) |

オラクルは「期待値をどう定義できるか」で選びます。

| オラクル | 期待値の定義 | 向いている対象 |
|---|---|---|
| 例示 | 入力に対する正確な出力を記述する | サイズ計算、イベントの順序、画素の色 |
| 不変条件 | 常に成り立つ性質を記述する | ツリーの親子関係と深さ、dirty list の整合 |
| ゴールデン | 保存した出力と比較する | 描画結果の意図しない変化 |
| 差分 | Flutter の挙動を正解として比較する | Flutter 由来の Widget / RenderObject |

差分オラクルは FloatSoda 固有です。Flutter を正解として使える対象は observable behavior に限られ、性能や並行性には使えません。判断の原則は、[APIDesign](APIDesign.md) の「Flutter 由来の observable behavior に差異を作らない」に基づきます。

## 2. 組み合わせを切る基準

3つの軸を掛け合わせると64マスになりますが、大部分は空欄で構いません。次の3つの基準で対象を絞り込みます。

1. **最小範囲**: 同じ不具合をより小さな範囲で観測できる場合、大きな範囲のマスは使いません。実機は「実機でしか観測できないもの」にのみ使います。
2. **オラクル成立**: その範囲で期待値を定義できないマスは使いません。例えば「非機能 × 差分」は、Flutter の性能が .NET の正解にはならないため、すべて空になります。
3. **シナリオ**: 「誰が、いつ、何をしたいか」を1文で説明できないマスは使いません。負荷、セキュリティ、アクセシビリティ(Semantics は非移植の方針)は、この基準により除外します。

この表はテストの抜けを見つけるために使います。テストが存在しないマスを機械的に埋める必要はありません。

## 3. 現在の配置(2026-09-09 時点)

64マスのうち、基準を通過したのは14マスです。件数は `[Fact]` および `[Theory]` の数です。

| 目的 | 範囲 | オラクル | 現状 | 根拠 |
|---|---|---|---|---|
| 機能 | 単体 | 例示 | ある | `tests/FloatSoda.Test` 412件、`tests/FloatSoda.Rendering.Test` 8件 |
| 機能 | 単体 | 不変条件 | 薄い | `[Theory]` 47件は存在するが、ツリーの不変条件を機械的に検査するヘルパーはない |
| 機能 | 単体 | 差分 | 手順のみ | CONTRIBUTING は Flutter 公式テストの参照を必須としている。テスト自体は例示として記述する |
| 機能 | 結合 | 例示 | 薄い | `WidgetBinding` を端から端まで動かすテストは、`Core/WidgetBindingTest.cs` と `Core/PointerInputIntegrationTest.cs` の2ファイルのみ |
| 機能 | 描画 | 例示 | ある | `GetPixel` による画素の検証が15ファイル、84箇所 |
| 機能 | 実機 | 例示 | 無い | デバイスのテスト手順は存在するが、テストハーネスは未着手 |
| 機能 | 実機 | 差分 | 文書のみ | [known-divergences.md](../.agents/skills/floatsoda-device-test/references/known-divergences.md) に9件。うち8件が `Test: — (not set)` |
| 回帰 | 単体 | 例示 | ある | バグ修正ごとの regression test の追加を [REVIEW.md](../REVIEW.md) で必須としている |
| 回帰 | 描画 | ゴールデン | 無い | 参照画像は0件。`GetPixel` で要件を満たしている間は優先度が低い |
| 非機能 | 結合 | 例示(閾値) | 未着手 | `tests/FloatSoda.Test/FloatSoda.Test.csproj` は BenchmarkDotNet を参照しているが、`[Benchmark]` は0件 |
| 非機能 | 結合 | 不変条件(並行性) | 薄い | スレッドを扱うテストは `Engine/IOTaskRunnerTest.cs` など数件のみ。レンダースレッドと Layer clone の競合は未検証 |
| 受け入れ | 実機 | 例示 | 手動 | `samples/` は CONTRIBUTING で「結合テストのシナリオを兼ねる」としているが、CI はビルドのみ実行する。実行には SteamVR が必要 |
| 受け入れ | 文書と API | 例示 | 手動 | junior-coder test(`.agents/skills/floatsoda-junior-coder-test`)として実績あり。LLM を使用するため CI には組み込まない |
| 受け入れ | 文書 | 例示(スモーク) | ある | `website/scripts/verify-dist.mjs` |

## 4. 既知の穴と優先順位

影響が大きい順に示します。

1. **Flutter との差異がテストで固定されていない。** 差異は意図した仕様であるため、テストで固定しなければ、次回の移植作業で気づかずに元の状態へ戻ってしまいます。9件のうち半分は実機を使わず、単体テストか結合テストで固定できます。分類の詳細は §5 を参照してください。
2. **結合テストが2ファイルしかない。** 差分更新の dirty 伝播や入力の配送経路は、単体テストでは確認できず、実機テストでは実行速度が遅すぎます。この中間の範囲にあたる結合テストを拡充します。
3. **BenchmarkDotNet が活用されていない。** 依存関係はありますが、ベンチマークが存在しません。「1フレームの予算内にレイアウトが収まるか」は、Booth 創作者のペルソナが最も気にする点であるため、ベンチマークを作成するか依存を外すかを決定します。

優先度が低い項目、または判断待ちの項目は次のとおりです。

- **ツリー不変条件のヘルパー**: ツリー操作の後に、親子関係と深さを検査する共通ヘルパーです。実装コストが低いため容易に追加できます。
- **ゴールデン**: SkiaSharp の更新により描画が変わる不具合を検知する用途に限ります。`GetPixel` で検知できない不具合が発生するまで導入を保留します。
- **`samples/` の位置づけ**: 規約上は結合テストのシナリオとしていますが、実行手段は実機のみです。実機シナリオとして扱うか、ヘッドレスで実行する仕組みを構築するかは未決定です。
- **ペルソナ2・3の受け入れ**: Unity 出身者が uGUI の語彙で理解できるかを確かめる手段がまだありません。シナリオは作成できますが実行手段がないため、項目名のみ残します。

## 5. Flutter との差異とテストの関係

差異の台帳は [known-divergences.md](../.agents/skills/floatsoda-device-test/references/known-divergences.md) です。ラベルによって記述すべきテストの方向性が逆転するため、**テストを作成する前にラベルを決定します。**

| ラベル | 作成するテスト |
|---|---|
| deliberate | 差異を固定するテスト。差異を元に戻すと失敗する |
| port mistake | 修正前に失敗し、修正後に成功する regression test |
| not ported | テストは作成せず、Issue を作成する |
| unlabelled | 先にラベルを決定する。この状態でテストを作成すると、バグを仕様として固定する恐れがある |

9件それぞれの範囲、テスト名、着手の順番は、台帳末尾の「Triage 2026-09-09」節に記録しています。

## 6. 片付けの計画

Phase 2 のリリース([Home](Home.md#ロードマップphase))後に着手します。順番は次のとおりです。

1. 差異の固定テストの作成。台帳の Triage 節の順序(#4 → #5 → #1 → #7)
2. 結合テストの拡充(dirty 伝播と入力の配送経路)
3. BenchmarkDotNet によるベンチマークを作成するか、依存を外すかの判断
4. 台帳の更新(#5 の Flutter 欄の書き直し、#2 と #3 の統合、#6 の分割)

各作業に着手した際は、§3 の表と §4 の一覧を更新し、日付を書き換えます。
